# EAFC Live Mobile — Phase 1 Proof of Concept

Proves one thing only: **can a hybrid mobile shell open the real,
official EA FC 26 Web App inside a native in-app WebView, let the user
log in normally, and inject our own JavaScript once it has loaded?**

If yes, Phase 2 ports the Chrome extension's actual companion logic
(card detection, market calculation, backend calls, overlay) onto the
same injection mechanism proven here. If no, this README's "still needs
verification" section becomes the list of what broke and why, which is
exactly what determines whether the Safari Web Extension fallback (or
something else) is the right path for iOS instead.

**This is Phase 1 only.** No card detection, no market data, no backend
calls, no real overlay. Just: landing screen → launch EA → EA loads → a
static `EAFC LIVE • CONNECTED` badge appears.

## Architecture chosen, and why

**Capacitor** (`@capacitor/core` + `@capacitor/ios` + `@capacitor/android`),
per your own stated preference, wrapping:

- iOS: `WKWebView` (Apple mandates WebKit for all iOS browsers/webviews -
  there is no alternative rendering engine available, including inside
  Capacitor).
- Android: the system `WebView` (Chromium-based).

**For the actual EA-hosting WebView + script injection specifically**,
this uses **`@capgo/capacitor-inappbrowser`** (npm, actively maintained,
Capacitor v8-compatible) rather than a hand-written native Swift/Kotlin
plugin. Reasoning:

- This sandbox has no Xcode and no Android SDK (`xcodebuild`/`adb` both
  absent), so any hand-rolled native plugin code could not be
  compile-tested here at all - the risk of shipping subtly-broken Swift/
  Kotlin was real. Depending on an existing, documented, already-built
  plugin removes that entire risk class and lets Phase 1 focus on the
  actual open question (does EA's login work in an embedded WebView at
  all), not "did I write correct WKWebView boilerplate."
- Its `openWebView()`/`executeScript()`/event-listener API is exactly
  the shape this needs: open an arbitrary URL in a native in-app
  WebView with a persistent (non-ephemeral) cookie/session store, get
  page-load and URL-change events, and inject JavaScript into that
  WebView on demand - see "How injection works" below.
- I verified the plugin name/version and its exact current API
  (`openWebView`, `executeScript`, `addListener('browserPageLoaded'|
  'urlChangeEvent'|'closeEvent', ...)`, `persistWebViewData`,
  `ToolBarType`, `CloseAction`) against its published source
  (`Cap-go/capacitor-inappbrowser` on GitHub) rather than from memory,
  specifically because shipping code against a stale/guessed API would
  have wasted your first test cycle for nothing.

No frontend framework (React/Vue/etc.) - plain HTML/CSS/JS, matching
`eafc-live-extension`'s existing no-framework style. The one build step
that does exist (`npm run build`, via `esbuild`) is there only because
the InAppBrowser plugin's own plugin-name resolution is dynamic per
platform internally - hand-rolling a `window.Capacitor.Plugins.X` lookup
to avoid a bundler would mean guessing that internal logic, which isn't
safe to do. `esbuild` was already proven to work in this environment
earlier in this project (used to validate `frontend/`'s JSX). This
build step **has been run and verified to succeed** in this
environment - see "What's actually been tested" below.

## Existing code reused

None of the Chrome extension's JS files are imported directly - the
injection *mechanism* is fundamentally different (Chrome
`content_scripts` declared in a manifest vs. an in-app WebView's
`executeScript()` call), so there was nothing to literally share for
Phase 1's single static badge. What *is* carried over deliberately:

- **The security model.** `shared/ea-badge.js` follows the exact same
  rules as `eafc-live-extension/src/overlay.js`: closed/self-contained
  UI, explicitly labelled "EAFC LIVE" (never "EA" alone), never reads or
  transmits anything from the host page, fails harmlessly if injection
  is retried.
- **The visual language.** `www/styles.css` reuses the same dark palette
  (`#14181f` panels, `#7fd8ff` accent, `#5fd98a` for "connected") as
  `eafc-live-extension/src/overlay.js`'s `STYLES`, so the two companions
  read as the same product.
- **The identity-mapping rule** (`resourceId`/`definitionId`, never
  `maskedDefId` alone) and the companion API contract
  (`GET /api/v2/companion/card/{source_card_id}`) are documented in this
  README's "Phase 2" section as the reuse target once card detection is
  actually ported, but neither is implemented yet - Phase 1 has no card
  detection at all.

Phase 2 is where actual code-sharing happens: `eafc-live-extension/src/
{card-detector,market-calc,eafc-api-logic}.js` are already plain,
DOM-free, UMD-wrapped modules (proven reusable across three different
JS execution contexts already - the Chrome extension's MAIN world,
ISOLATED world, and its background service worker). The same files
should attach to `window.EAFCLive` just as well inside the EA
in-app-browser's WebView, unmodified or nearly so - see "Longer-term
product direction" for the plan.

## iOS implementation

Capacitor wraps `WKWebView` for both the app's own landing screen and
(via the InAppBrowser plugin) the EA WebView. No custom Swift was
written for Phase 1 - see the architecture rationale above. Once you run
`npx cap add ios`, Capacitor generates a real Xcode project at `ios/App`
that `npx cap sync` keeps in sync with `www/` and this package's
dependencies.

## Android implementation

Same story: Capacitor wraps the system `WebView`. `npx cap add android`
generates a real Android Studio (Gradle) project at `android/`.

## How WebView injection works

1. User taps **Launch Web App** (`www/index.html`'s `#launch-btn`).
2. `src/app.js` calls `InAppBrowser.openWebView({ url: EA_WEB_APP_URL,
   persistWebViewData: true, toolbarType: ToolBarType.NAVIGATION,
   showReloadButton: true, closeAction: CloseAction.CLOSE })`. This opens
   a **native** in-app WebView (not a second copy of our own app, not a
   proxy - the plugin loads EA's real URL directly) with a visible
   native toolbar (title, reload, close).
3. The plugin fires `browserPageLoaded` once that WebView finishes
   loading a page, and `urlChangeEvent` on every URL change inside it
   (including SPA-style in-app navigation that doesn't do a full
   reload).
4. `src/app.js` checks the loaded URL against `/ultimate-team.*web-app/i`
   - the same "is this actually the Web App, not an EA login/account
   redirect page" test the Chrome extension's `manifest.json` match
   pattern encodes. Only then does it call `InAppBrowser.executeScript({
   code: EA_BADGE_SCRIPT })`.
5. `shared/ea-badge.js` runs **inside EA's own page**, in EA's own
   origin - it creates one small, `pointer-events:none`, fixed-position
   `<div>` labelled `EAFC LIVE • CONNECTED` and appends it to
   `document.body`. An idempotency guard (`window.__eafcLiveBadgeInjected`)
   means a second `executeScript()` call (from `urlChangeEvent` firing
   again) is a safe no-op, not a duplicate badge.

This mirrors the Chrome extension's page-bridge/content.js relationship
conceptually - "observe the page's own lifecycle, then paint a small,
clearly-ours UI element" - just triggered by explicit plugin events
instead of a declarative manifest.

## How authentication remains owned by EA

- The in-app WebView navigates to EA's **real** URL
  (`https://www.ea.com/ea-sports-fc/ultimate-team/web-app/`, currently -
  see the open question about locale below). This app never renders its
  own login form, never sees a password field, never intercepts a
  submit.
- `persistWebViewData: true` (the plugin's default, set explicitly here
  so it's visible rather than implicit) controls only whether **EA's
  own cookies**, inside the **native WebView's own storage**, persist
  across app restarts - the same thing a browser remembering a login
  does. This app's own JavaScript never reads that cookie jar; the
  plugin's API surface (`openWebView`/`executeScript`/`postMessage`)
  has no method that exposes cookies or headers to this app's JS layer
  at all.
- `shared/ea-badge.js` reads nothing from the page - not `document.
  cookie`, not any DOM field, not any request. It creates one `<div>`
  and stops.
- Nothing in this codebase ever sends a request to `api.eafc.live`
  carrying anything from the EA session (Phase 1 doesn't call the
  backend at all yet; Phase 2's plan for this is in "Longer-term
  product direction").

## Security decisions

- No custom native code (this Phase) → no native surface that could
  accidentally read WebView storage/cookies beyond what the vetted,
  published plugin already does.
- `shared/ea-badge.js` is `pointer-events: none` and reads nothing from
  the page - by construction, not merely by convention, it cannot
  intercept a tap meant for EA's UI or exfiltrate anything.
- The badge is explicitly labelled `EAFC LIVE`, styled distinctly from
  EA's own UI (rounded pill, our brand accent color) - never presented
  as if EA built it.
- `capacitor.config.json` declares no `server.url`/remote-content
  override and no unusual permissions - the app's own landing screen is
  bundled, local content only; only the InAppBrowser plugin's own
  WebView ever navigates to a remote origin.
- iOS/Android permissions the plugin's README lists (camera, microphone,
  location - for in-page features like Google Pay or file uploads that
  need device APIs) are **not** added to `Info.plist`/
  `AndroidManifest.xml` here, since Phase 1 (and the Transfer Market
  browsing this is ultimately for) doesn't use any of them - keeps the
  app's permission footprint, and App Store/Play Store review surface,
  minimal. Add only the ones actually needed if a later phase does.

## What's actually been tested (and what hasn't)

**Verified in this environment:**
- `npm install` succeeds cleanly against the pinned versions.
- `npm run build` succeeds - `esbuild` bundles `src/app.js` (with a real
  `import` of `@capgo/capacitor-inappbrowser`) plus the inlined
  `shared/ea-badge.js` string into `www/app.js` with no syntax errors
  (`node --check` passed against the output).
- `npx cap doctor` recognises the project and reports all four
  Capacitor packages at their latest matching versions.
- `capacitor.config.json` is valid JSON.

**NOT verified, and cannot be from this environment (no Xcode, no
Android SDK, no iPhone/Android device, no EA account session):**
- Whether `npx cap add ios` / `npx cap add android` succeed - this
  needs your local Xcode / Android Studio.
- Whether the generated native projects actually build and run on a
  simulator/device.
- **The actual open question this whole PoC exists to answer**: whether
  EA's login flow works normally inside this in-app WebView at all - no
  detection/blocking, no CAPTCHA loop specific to embedded WebViews, no
  "please open in a real browser" refusal. This is the single most
  important thing to check on first real-device test, exactly as you
  flagged.
- Whether `www.ea.com/ea-sports-fc/ultimate-team/web-app/` (no locale
  segment) is a valid entry point that auto-redirects, or whether an
  explicit locale (`/en-us/`, `/fr-fr/`, etc.) is required. If it 404s
  or shows the wrong thing, this is the one constant to fix
  (`EA_WEB_APP_URL` in `src/app.js`).
- Whether `browserPageLoaded`/`urlChangeEvent` fire reliably through
  EA's actual login redirect chain (which may hop through a distinct
  `signin.ea.com`/`accounts.ea.com` origin before landing back on
  `ea.com`) such that the badge injects only once the *real* Web App has
  loaded, not mid-redirect.
- Whether the session survives fully closing and reopening the app (this
  should follow from `persistWebViewData: true`, but "should" isn't
  "confirmed").
- Whether EA's own CAPTCHA/challenge system (if one appears) renders and
  completes correctly inside this WebView, or blocks it.

## Build/run instructions

### What you need installed locally

- **Node.js** (any recent LTS; this was built/tested against Node 22)
  and npm.
- **For iOS:** a Mac, Xcode (current stable), and CocoaPods (Xcode
  usually prompts to install this, or `sudo gem install cocoapods`).
  A free Apple ID is enough to run on your own device via Xcode; no
  paid developer account needed for local device testing (only for App
  Store distribution later).
- **For Android:** Android Studio (which bundles the Android SDK) on
  Mac, Windows, or Linux.

### One-time setup

```bash
cd eafc-live-mobile
npm install
npm run build          # produces www/app.js - required before cap add/sync
npx cap add ios         # only on a Mac with Xcode installed
npx cap add android      # needs Android Studio/SDK installed
```

### Every time you change src/app.js, shared/ea-badge.js, or www/*

```bash
npm run sync            # = npm run build, then `cap sync` (copies www/ into both native projects)
```

## Exact steps for testing on a real iPhone

1. Complete "One-time setup" above on a Mac.
2. `npx cap open ios` - opens the generated project in Xcode.
3. Plug in your iPhone via USB (or pair it wirelessly in Xcode's Devices
   window).
4. In Xcode's top toolbar, select your iPhone as the run destination
   (instead of a simulator).
5. Xcode → **Signing & Capabilities** tab (select the "App" target)→
   choose your own Apple ID under "Team" (Xcode will offer to create a
   free personal team if you don't already have one signed in under
   Xcode → Settings → Accounts).
6. Press **Run** (▶). Xcode builds, installs, and launches the app on
   your phone.
7. First run only: on the iPhone, go to **Settings → General → VPN &
   Device Management**, and trust your own developer certificate (iOS
   blocks launching a freshly-installed dev build until you do this
   once).
8. Open the app, tap **Launch Web App**, log into EA normally, and watch
   for the `EAFC LIVE • CONNECTED` badge in the bottom-right once the
   Transfer Market / Web App itself has loaded.
9. Check Xcode's own console (View → Debug Area → Activate Console, or
   the bottom panel while running) for any `[EAFC Live]` `console.error`
   lines if the badge doesn't appear - `src/app.js` logs there on any
   `openWebView`/`executeScript` failure.

A free Apple ID's signing certificate expires after 7 days, so you'll
need to re-run from Xcode weekly for continued local testing (this is
an Apple platform limitation, not something specific to this app).

## Exact steps for testing on Android

1. Complete "One-time setup" above (Android Studio installed).
2. `npx cap open android` - opens the generated project in Android
   Studio.
3. On your Android phone: **Settings → About phone** → tap **Build
   number** 7 times to enable Developer Options, then **Settings →
   System → Developer options** → enable **USB debugging**.
4. Plug the phone in via USB; accept the "Allow USB debugging?" prompt
   on the phone.
5. In Android Studio's device dropdown (top toolbar), select your phone
   instead of an emulator.
6. Press **Run** (▶). Android Studio builds, installs, and launches the
   app.
7. Tap **Launch Web App**, log into EA normally, watch for the badge.
8. Check Android Studio's **Logcat** panel (filter by your app's package
   `com.eafclive.mobile`, or search for `EAFC Live`) for any injection
   errors if the badge doesn't appear.

No special certificate/signing step is needed for local device testing
on Android (unlike iOS) - a debug build installs directly.

## App Store / Play Store concerns

Not relevant yet (Phase 1 is local-device testing only), but worth
flagging now since they'll matter once this moves toward real
distribution:

- **Embedding a third party's authenticated web experience inside your
  own app** is exactly the kind of thing both Apple and Google review
  guidelines scrutinize - not necessarily disallowed, but expect
  questions, and expect this to be one of the first things a reviewer
  tests manually. Read EA's own Terms of Service /
  developer-facing terms regarding third-party clients before any store
  submission - this was explicitly out of scope to investigate here and
  needs separate legal/ToS review, not just a technical check.
- **This app requests no unusual permissions** (see "Security
  decisions") - that's a genuine plus for review, keep it that way
  unless a real feature needs otherwise.
- If EA's login flow uses a **third-party OAuth provider** (e.g. "Sign
  in with Google") at any point, be aware Google's own policy blocks
  its OAuth from completing inside embedded/generic WebViews
  (detected via user-agent) - this would surface as that *specific*
  login path failing while EA's own direct email/password login
  continues to work fine. Worth explicitly testing both if EA offers a
  choice.
- Confirm before public distribution whether this qualifies as
  "official EA SPORTS FC content" requiring EA's permission/branding
  guidelines review - again, a legal/business question, not a technical
  one, and explicitly not assessed here.

## Longer-term product direction (Phase 2+, not built yet)

Once Phase 1 is confirmed working on a real device:

1. **Sanitized WebView bridge.** `shared/ea-badge.js` becomes the seed
   for a real companion-core script: reuse
   `eafc-live-extension/src/card-detector.js`'s
   `extractAuctionsFromResponse`/`groupAuctionsByCardId` logic (already
   plain, DOM-free, UMD-wrapped - proven to attach to a global object in
   three different JS contexts already) to parse `/transfermarket`
   responses **inside the EA WebView's own JS**, exactly like
   `page-bridge.js` does for Chrome - sanitized down to `{sourceCardId,
   tradeId, rating, buyNowPrice, currentBid, startingBid, expires,
   tradeState}` per auction, never the raw response, before anything
   leaves that page's JS context.
2. **Bridge to the app's own privileged context.** The sanitized payload
   goes from the EA WebView to this app's own JS (the landing-screen
   context, i.e. `src/app.js`'s world) via the InAppBrowser plugin's
   `window.mobileApp.postMessage()` / `messageFromWebview` event - the
   mobile equivalent of the Chrome extension's `chrome.runtime.
  sendMessage()` call from content script to background service worker.
3. **Companion API calls happen from the app's own context, never from
   inside the EA WebView** - same reasoning as the Chrome extension's
   `background.js`: a request made from *inside* EA's origin would be
   subject to `api.eafc.live`'s CORS allowlist (`app.futhub.co.uk`/
   `app.eafc.live`/localhost only - deliberately not loosened for this),
   so it would be blocked exactly the way a raw content-script `fetch()`
   was for Chrome. Calling `GET /api/v2/companion/card/{source_card_id}`
   from the app's own privileged context sidesteps that the same way the
   background service worker did.
4. **Combine + render** reuses `eafc-live-extension/src/market-calc.js`
   (`combineIntelligence`, `verdictLabel` - already pure, no DOM) as-is,
   and a new mobile-specific overlay renderer (touch-friendly,
   collapsible, safe-area-aware per the mockup in the original request)
   replaces the desktop `overlay.js`.
5. Never independently invent a BUY signal from live EA data alone -
   the same rule enforced in `market-calc.js::combineIntelligence`
   already (`insufficient_data`/non-buy signals can only ever render
   "not a buy", regardless of how cheap the live BIN looks) applies
   unchanged.

Eventually: native EAFC Live sections (Opportunities, Trade Finder,
Watchlist, Portfolio, Player Search, Notifications, Settings) alongside
the embedded EA Web App, which becomes one section ("Companion") of a
larger native app - not attempted in this phase.
